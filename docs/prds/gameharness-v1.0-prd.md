# GameHarness 1.0 product requirements

Status: release acceptance specification, broader than the delivered bounded Minecraft workflow. The [integration guide](../integration-spike.md) records supported setup, current gameplay evidence and historical cohorts. The reviewed two-trip custom task establishes a narrow end-to-end result, not completion of every release criterion below. Unchecked criteria remain open unless their full evidence requirement is met.

## Product goal

GameHarness is a standalone desktop application for configuring, watching and supervising one LLM-controlled player. The principal model observes, plans, writes ordinary modular programs, acts, checks consequences, repairs procedures and recovers toward one high-level objective. Disclosed mechanical helpers, optional local-code/Jev reactions and retained experience support execution independently of strategic reasoning. Movement, repeated failed actions and a busy feed cannot substitute for useful progress.

The product supports game integrations through explicit adapters. An adapter supplies a game's observation profile, bounded action capabilities, live view, task verification, and supported lifecycle operations. Generic orchestration handles planning, scheduling, policy execution, persistence, providers, and operator controls. Adding another game requires an adapter and evidence that it conforms to those contracts; there is no claim of automatic or zero-configuration universal support.

Minecraft is the first implemented integration and the reference for the complete-integration requirements. Its concrete requirements appear in the [Minecraft profile](#first-reference-integration-minecraft). A second implemented game is not a prerequisite for this release, and Minecraft-specific mechanics must not become mandatory core schemas.

There are two audiences: an operator who configures an installed adapter, providers, environment, and task on the supported Linux host; and a viewer who sees live play and an accurate activity feed. Setup must be understandable to an external user on that host. Hosted operation, multiuser accounts, and arbitrary cross-platform compatibility are outside the initial release.

The agent should use understandable high-level strategies and permitted player information. Low-level calculations need not imitate human thought. Explanations use source and event evidence, without claims to expose hidden chain of thought.

## Readiness and game outcomes

| Dimension | Required evidence | Reporting boundary |
| --- | --- | --- |
| Workflow readiness | Documented supported-host setup, real provider connection, adapter connection, autonomous play, live display, controls, durable experience, and recovery work together. | An isolated model call or disconnected UI cannot establish readiness. |
| Useful continuity | Held-out runs meet declared progress and non-regression criteria, with planning idle time, action outcomes, failures, and policy behavior recorded. | Constant motion and short response latency alone cannot establish useful play. |
| Task outcome | An adapter-defined verifier establishes completion, failure, or unresolved progress for the selected task. Tasks may be bounded goals or whole-game objectives. | A narrower subgoal must not be reported as completion of a larger objective. |
| Integration support | The adapter's tested versions, observation profile, capabilities, limitations, and conformance evidence are published. | One integration's working checkpoint, renderer, or cancellation mechanism does not establish support in another game. |

Report workflow readiness, continuity, integration support, and task outcomes separately. A usable workflow can be ready while a difficult game-completion objective remains unachieved. The unachieved objective and furthest verified progress remain visible; workflow readiness must never imply a successful game completion. Engineering verification uses the four tiers and shared finite live-attempt policy in [learning and evaluation](../learning-and-evaluation.md#verification-and-live-evaluation-policy). Platform conformance and agent performance remain independent results.

## Game adapter extension boundary

The canonical `GameAdapter` descriptor is owned by [runtime contracts](../runtime-contracts.md). Product requirements for that boundary are:

| Adapter responsibility | Required declaration and behavior |
| --- | --- |
| Identity and compatibility | Declare `game_id`, `adapter_id`, `adapter_version`, supported observation schemas/profiles, and version constraints. Runs and experience artifacts retain game, adapter, and observation-profile identity. `world_id` identifies a game world, level, or session lineage rather than requiring a Minecraft world. |
| Permitted observations | Define player-observable fields, visibility/freshness rules, unknown values, and remembered observations. The core carries declared data without requiring blocks, entities, recipes, health, or hunger fields. |
| Action capabilities | Publish typed capability schemas, effect preconditions, outcomes, deadlines, and cancellation behavior. The scheduler works with declared actions rather than a mandatory Minecraft action enum. |
| Connection and effects | Implement connect, observe, effect, and cancel contracts with explicit support levels and failure semantics. If cancellation cannot be acknowledged, declare the fencing or recovery needed before another effect owner can act. |
| Live view | Supply a view source with run/environment identity and availability status. View transport is adapter-specific, and viewer access cannot bypass the agent's observation permissions. |
| Task verification | Declare supported task verifiers, evidence sources, and any verification-only privileged access. Verification-only state remains outside planner, policy, and transferable experience inputs. |
| Environment lifecycle | Declare save/checkpoint, reset, restore, and reconnect/recovery capabilities independently, including unsupported operations and consistency limits. There is no universal save/restore guarantee. |

Extending GameHarness requires implementing this boundary, documenting installation and permissions, mapping game mechanics to bounded capabilities, declaring task verification and recovery support, and collecting conformance evidence. Conformance covers real connection and effects, observation isolation, view identity, cancellation or safe recovery, stale-result rejection, and task evidence. The extension procedure uses the existing runtime interfaces; a speculative plugin framework or fictitious second integration is unnecessary.

## Required user flow

1. **Prepare the host and adapter.** Follow supported-host instructions for the application and chosen game integration. The operator supplies lawful game access and accepts relevant terms. Instructions name tested versions and limitations; distribution must not include game binaries or account secrets without authorization.
2. **Connect providers.** Configure a supported API-key or legitimate provider-supported subscription/OAuth connection, select a strategic model, and enable or disable Jev. Display usable, expired, unsupported, unavailable, and failed connections accurately. Verify entitlement for the operator; a consumer subscription does not itself establish API access. Configuration alone must not be labeled a verified provider connection.
3. **Configure a run.** Select an installed adapter, supported environment, task, and cold or compatible inherited experience snapshot. Show the actual start, materialized observation/RGB assistance profile and enabled optional backends before starting. A profile-selector UI is not required, but comparisons must freeze the selected profile explicitly. Environment creation, loading, prepared-task and reset choices depend on genuine adapter support.
4. **Start with host preflight.** Create an identifiable run and expose its actual lifecycle. The host checks readiness and fresh authorized state; a short executable instruction explains program workflow and limits, with exact reference behind generated help. No multi-request model ceremony reconfirms host-known facts. Compatible model-authored warm selections hydrate through normal validation and fenced activation without mandatory reauthoring or repeat tactical trials. Declare finite bounds equally across matched arms. An absent reaction stays visible and does not prevent ordinary program gameplay.
5. **Watch autonomous play and improvement.** Display the adapter's live view and a feed distinguishing intent, accepted work, outcomes, interruptions, waits, and failures. Strategic reasoning overlaps bounded execution and reactive evaluation; a model turn cannot lock the game action loop. Event-driven strategic turns receive proactively formed improvement opportunities. The model retrieves experience, authors or revises behavior, judges a bounded trial, or explicitly defers/rejects the opportunity with reasons. A minimal improvement-history card links actual version changes, semantic explanations, and measured or not-yet-measured outcomes.
6. **Control execution.** Pause stops new effects and reaches an acknowledged paused state only after actual native neutralization and full run-emitter drain. Resume reobserves without replaying old work. Stop run and goal completion also retain a healthy session/video; explicit Stop world, world replacement and desktop close end owned game processes. Unconfirmable control failure still requires fail-closed recovery. Stop remains available during inference, actions and backend failures. Task and provider controls configure a new run; midrun model switching is optional.
7. **Retain and reuse experience.** Record permitted observations, action outcomes, immutable artifact versions, mandatory StrategyCards, and provenance. Separate knowledge, reusable skill programs, and short policies. Selectively search summaries, retrieve exact artifacts on demand, save knowledge, inspect performance history, and propose promotion through the [experience interface](../runtime-contracts.md#selective-experience-interface). Eligible model proposals create new immutable cross-session snapshots without mandatory human approval; trusted evidence and portability gates reject or defer ineligible proposals. A warm run selects compatible experience without importing another environment's private layout or incompatible game assumptions.
8. **Recover or finish.** Fence old work, reconcile uncertain actions against authoritative current state, and resume only when the adapter's recovery requirements are met. Completion, stop, failure, infrastructure repair, and human interventions remain identifiable in the evidence.

Ordinary player death is a life transition inside the same session and active run, not a client error or automatic terminal failure. Fence old-life commands/targets/reaction/planning results, retain authentic DeathScreen video and deliver compact death evidence to one strategic wake. Only an explicit model-selected vanilla respawn through the action arbiter starts a new life after authoritative readiness; saved-dead startup never respawns automatically. Session/epoch stay unchanged, and all unrelated old-life work remains fenced.

## Scope and priorities

### Required for the initial release

- One complete reference integration on the supported Linux host, built through the game adapter boundary, with real provider requests and game effects.
- An adapter-supplied live view, truthful activity feed, and select/start/stop/pause/resume, task, and provider controls.
- One controlled player, one strategic LLM, and independent planning, execution, and reactive evaluation with one foreground action lease. A fast helper model remains part of this single-player control design.
- An event-driven Strategic Turn Scheduler and Autonomous Improvement Loop inside the trusted backend, with one strategic request at a time, durable opportunity handling, evidence-linked model decisions, and bounded real trials.
- Ordinary model-authored JavaScript modules, controlled pure-library resolution and coherent bounded execution. Local-code reactions and optional Jev remain available according to the declared implementation; code-only operation works without a helper model and backend failure stays explicit.
- OS-isolated generated programs using brokered capabilities and filtered player-observable information.
- Durable run/event/action evidence, selective retrieval, evidence-gated promotion, compatible warm activation, explicit compatible cross-model imports and checkpoint recovery that preserves uncertainty rather than blindly repeating effects.
- Mandatory StrategyCards for reusable versions and a minimal live improvement-history card with authorized source/event evidence.
- Bounded persisted actual execution traces, categorized waits, objective version comparisons and model-authored revision candidates; neither branch/intent text nor unmeasured edits establish improved behavior. Same-session/model working definitions remain distinct from qualified cross-session memory.
- Optional, explicit bounded lookahead that stages no effects and requires fresh session/life/task/predecessor/source identity and isolated read-only preconditions before activation. Verified-goal review is bounded and effect-free, without extra gameplay trials.
- Real cold/warm evaluation, a controlled policy-capability experiment, held-out useful-progress evidence, declared task outcomes, progressive reliability evidence, and honest operating documentation.
- Real supported API-key and subscription/OAuth paths, plus adapter-verified success on the same bounded task by two strategic models from different providers without core or adapter edits.

### Optional additions

Separate code-only/Jev-only/asynchronous controller ablations, replay/event/video browsing, export UI, extra dashboards, full library browsers/editors and midrun model switching are optional. Jev is an optional backend, not a prerequisite for the first complete chain. The controlled capability experiment, explicit compatible cross-model product reuse and minimal live improvement-history view remain required. Event or video replay does not imply deterministic environment rewind.

### Initial non-goals

Multiple playing agents, CV-only control, reinforcement learning, fine-tuning, model-weight training, human strategy trials, speedrunning records, and scientific novelty claims are not required. Public multiplayer hosting, public internet deployment, and account management are excluded. Additional games are supported by the extension design; implementing a second adapter is not required for the initial release.

## Authorship and information boundary

Programmer-authored infrastructure supplies connection lifecycle, filtered observations, disclosed bounded mechanical/GUI helpers, scheduling, safety, persistence, providers, UI, measurements and recovery. The principal model owns resource strategy, game plans, procedural composition, reactive conditions, backend choices and evidence-driven revision. A recipe helper may execute a selected recipe with available ingredients, not recursively gather its prerequisites. Richer authored controllers require a separate assistance/comparator label.

Adapters must not hide developer-written strategic routines behind convenience capabilities. The model chooses destinations and exploration strategy. Trusted navigation may use an adapter's explicitly declared private local-geometry permission for bounded movement and local detours toward the same authorized known target, without every collision cell having been observed. That permission cannot select global or unknown exploration routes from hidden geometry or expose hidden targets. Minecraft's bounded exception is defined in the [runtime contracts](../runtime-contracts.md#bounded-private-navigation-geometry). Public game documentation, recipes where applicable, pretrained model knowledge, and brokered web retrieval are allowed. Cold and warm runs retain the same bootstrap, programming, Jev, and retrieval capabilities; cold means no inherited experience.

Player-observable permission is interpreted by each adapter's observation profile, independently of whether its interface is structured state/events or images. Structured data is not automatically fair; screenshots and strict camera simulation are not required for information fairness. Unobserved state remains unknown rather than absent. Agent tools, generated code, navigation outputs, error messages, retrieval, and renderer access must obey the boundary; trusted controller-only geometry is not an agent observation. A trusted evaluator may access privileged state only to verify outcomes, outside the planner and skill-memory path.

## Requirements and observable acceptance

The checkboxes below track the full release criteria, not a claim that their component mechanisms lack evidence. Current scoped results belong in the integration guide. Core workflow criteria and reference-profile outcomes must be reported independently.

### Setup and operation

- [ ] **P01 — Supported-host workflow.** An operator completes documented setup, connects an installed adapter to a supported environment, and reaches real autonomous gameplay. Instructions identify tested application, runtime, adapter, and game versions without implying untested compatibility.
- [ ] **P02 — Both auth categories.** A supported API-key connection and a legitimate provider-supported subscription/OAuth connection each make a real authorized request through their documented flow. Credentials remain trusted; unsupported entitlement or expired access produces an actionable error. Publish the supported-provider matrix; this is not a promise of every provider or subscription brand. The first playable gate may use one category, but release acceptance requires both.
- [ ] **P03 — Essential controls.** Start, pause, resume, and stop work during inference and bounded effects. Displayed lifecycle states follow acknowledged runtime state. Task/provider changes can configure a new run without optional midrun switching.
- [ ] **P04 — Truthful desktop view.** One visible GameHarness window shows the actual controlled Fabric client's post-HUD world/hand/video, not a reconstructed Mineflayer scene. Gameplay occupies at least 75% of the fixed main area with the hideable sidebar visible and nearly all of it hidden; setup/source/cards/evolution/history use bounded dialogs. Video is read-only and separate from control. The feed distinguishes proposals, completion, waits, failures and uncertainty; video freshness and observation permission are independent.

### Autonomous control

- [ ] **P05 — Bounded startup and warm activation.** Cold and warm runs use the same capability description and host-preflight policy, with per-model limits frozen equally across matched arms. Record limits, actual requests/exposed attempts, retrieval, validation/cache, activation and first effect. Eligible exact-version model-authored warm selections use ordinary compatibility, isolation, freshness and fencing without mandatory regeneration or repeat tactical trials; zero strategic authoring calls is permitted. Unselected source stays behind selective retrieval. Missing/inapplicable entries and ordinary authoring remain visible, without a silently empty/substituted library. Host readiness requires no model ceremony, and no developer tactic makes startup appear successful.
- [ ] **P06 — Concurrent and composite control.** A real long model request overlaps a bounded effect and reactive evaluation. Strategic submission returns the corresponding action or skill-execution identifier promptly. One bounded composite input coordinates simultaneous movement, camera change, and permitted interaction/attack under a single lease; cancellation neutralizes every included channel. Measurements distinguish model latency, runtime dispatch/reaction latency, meaningful game waits, and LLM-induced idle time.
- [ ] **P07 — Declared reaction backends.** Code-only execution works without Jev or mandatory reflex-authoring ceremony. When the model selects a local-code reaction or the optional Jev backend, retain actual authoring/use/outcome evidence and bounded freshness/authority behavior. Advertised Jev support requires a real provider result; unavailable/failed Jev stays explicit and local execution never impersonates it.
- [ ] **P08 — Single effect owner.** Competing policies, revisions, pause, and stop cannot issue conflicting independent player effects. Transfer requires acknowledged cancellation/neutralization or the declared safe recovery path. Old-epoch work cannot act; ambiguous effects remain unknown.
- [ ] **P09 — Useful continuity.** Held-out runs meet frozen continuity criteria from [learning and evaluation](../learning-and-evaluation.md), including an explicit observation window and adapter/task-specific progress/non-regression rule. Report control-only Time to Fluidity independently of task efficacy, progress, non-regression, and deaths for the same window. Good control timing alone does not establish useful play; repetitive motion cannot count as task success. Include failures and all planned runs.
- [ ] **P10 — Ordinary bounded programs.** The model writes coherent JavaScript modules with relative local imports, controlled pure-library resolution and a stable `run(game, args, checkpoint)` entry. The host owns immutable source/dependency identity, scope, finite source/transport/runtime/capability limits and retry admission. Pure local calls share the isolated execution. Observe/write/run/inspect/revise does not require detailed artifact forms before a first attempt; reusable versions still need complete provenance and evidence. Line count and complexity are descriptive, not quality gates. Custom completion prose cannot replace independent verification, and source validation cannot replace OS isolation.

The current [compact-body interface](../runtime-contracts.md#current-compact-program-interface) is narrower: 16 KiB bodies, exact-version child calls and no module imports or checkpoint continuation. It remains the current callable contract until the module cutover; it does not satisfy the complete target above merely by accepting a larger body.

### Experience, safety, and recovery

- [ ] **P11 — Compatible reusable experience.** Warm runs select an immutable snapshot. Bounded summary search, exact retrieval, idempotent knowledge/promotion proposals and actual outcome history work through the [experience interface](../runtime-contracts.md#selective-experience-interface). Explicit cross-model product imports preserve authoring provider/model provenance and recheck source, profile, capabilities and applicability; comparisons never silently cross model/library partitions. Knowledge retains permitted provenance, uncertainty and supporting/contradicting evidence; executable artifacts additionally require complete cards and eligible gameplay evidence. Eligible model proposals create a new snapshot without mandatory human approval. Rejected, inconclusive and failed versions remain visible. Lost acknowledgements cannot duplicate versions, selected snapshots never mutate, and sealed comparisons defer publication until closure. World state remains with its lineage; held-out starts never train the evaluated library.
- [ ] **P12 — Observation and sandbox boundary.** Tools, generated code, navigation, errors, retrieval and view routes expose no forbidden game state, host files, secrets or arbitrary network. Exercise the [profile conformance fixtures](../operations-and-security.md#structured-observation-and-navigation): the assisted-360 condition permits nearby unobstructed behind-camera objects, the frustum condition gates new world targets, and a strict-visual claim has no semantic-object/private-geometry bypass. Concealed resources stay hidden, hidden entities have no exact live tracking, memory stays stale and real audio is coarse. Unknown is not absent. Where declared, bounded private geometry supports local detours toward the same authorized target, never hidden resource/global exploration selection or path/count/error leakage. Reject unknown targets before lookup; test internal reads/effects with Anti-Xray disabled and record optional Paper configuration. Alternate endpoints cannot bypass filtering. Invalid code remains bounded/quarantined, and security fixtures establish neither learned tactics nor gameplay efficacy.
- [ ] **P13 — Durable recovery.** Versioned serializable task checkpoints support compatible restart without restoring stacks or blindly repeating effects. Resume requires fenced/drained prior owners, fresh authorized state and reconciled unresolved operations, preserving explicit Pause/Stop. Game reset/restore follows actual adapter support; any rollback is explicit and memory is reconciled. Source or conversation restore never rewinds the world.
- [ ] **P14 — Long-running operation.** Progressive soak evidence covers extended real play and recovery toward the hours/days target. State actual tested duration, infrastructure downtime, game failures, and interventions; short sessions cannot establish days-long reliability.
- [ ] **P15 — Usage transparency.** Retain logical decisions, actual requests/attempts and available IDs, uncached input, cache read/write, output, calls and known/unknown cost separately. Host role/reason assigns provisional purpose at admission; documented precedence over visible returned tool calls finalizes it after the response. Missing responses remain explicitly provisional. No extra model call, prose/source interpretation or hidden reasoning is required for accounting. Preserve aggregate-only legacy usage as unclassified. Compact strategic context and selective detail retrieval must not become guaranteed token/cost-saving claims. Reliability controls operate independently of monetary reporting.

### Evaluation and extension

- [ ] **P16 — Registered comparative evidence.** Cold/warm and [controlled policy-capability experiments](../learning-and-evaluation.md#required-policy-capability-experiment) use immutable finite manifests, matched actual initial-save identities, sealed snapshots and every scheduled outcome. Freeze strategic model/provider, task/verifier, effective observation/assistance/server configuration, mechanics, executor, references and limits. A seed alone is not a matched save. The policy control disables registered reactions/fast requests; treatment enables the declared local-code and optional Jev package. Both retain ordinary conditional programs, and cold arms inherit no experience. Report task progress/non-regression/deaths independently from control timing and policy use, with failures, non-use, regressions, elapsed/downtime and usage retained. A package effect does not isolate Jev value. Predeclared sample reuse retains the same run IDs rather than manufacturing independent observations; within-run revision correlation is not causal improvement.

The implemented study gate currently supports only cold fresh seeded whole-agent natural tasks and an explicit no-inference admission mode. It refuses inherited/restored/prepared/frozen/Jev conditions before external calls. Those refusals preserve the integrity of these still-unpassed comparative requirements; they do not implement matched-save or warm experiments.

- [ ] **P17 — Task outcomes.** Declare each supported objective and verifier, retain genuine attempts, and report verified completion or exact unresolved progress. Tasks need not have a terminal game state. Narrow subgoals do not establish completion of broader objectives.
- [ ] **P18 — Adapter conformance.** The first integration uses the declared adapter interface. Evidence covers typed observations/actions, real effects, view identity, task verification, cancellation/recovery, stale-result fencing, and privileged-state isolation. Document unsupported lifecycle capabilities. No second implementation is required to establish this first adapter's support.
- [ ] **P19 — Honest operating handoff.** Documentation matches delivered setup, auth, tested integrations, limitations, and observed outcomes. State workflow readiness independently from task completion and unachieved reference-profile objectives.

### Improvement and model portability

- [ ] **P20 — Autonomous strategic turns and improvement.** The [Strategic Turn Scheduler](../runtime-contracts.md#strategic-turn-scheduler) wakes on host readiness, task changes, decision-relevant action/skill outcomes, policy replan, recovery completion, no runnable work, and due improvement/trial feedback. Known queued work can continue without another model call. Durable cursors, coalescing, bounded context/queues, finite retries, backoff, and explicit waiting/terminal states prevent tick polling and tight call loops. Only one strategic request runs at a time; late output remains fenced by existing freshness and stop rules. The [Autonomous Improvement Loop](../runtime-contracts.md#autonomous-improvement-loop) proactively offers evidence-backed repeated-gap, capability/error/interruption, short-sequence, boundary, and trial-decision opportunities at eligible turns without stopping gameplay just to analyze, using the runtime's configurable manifest-recorded trigger defaults. Dedupe/merge, durable acknowledgement/deferral, and one active improvement trial per run prevent lost or repeatedly rediscovered work across restart. At least one real opportunity leads to a model-authored change and linked bounded gameplay trial. Each offered opportunity receives evidence-linked reuse, author/revise/trial, keep/retire/revert, or explicit defer/reject disposition; runtime facts never prescribe tactics.
- [ ] **P21 — StrategyCards and visible improvement history.** Every reusable skill/policy version has the mandatory [StrategyCard](../learning-and-evaluation.md#human-readable-strategy-artifacts) fields: stable card/version and immutable source/config reference, purpose, applicability/limitations, understandable gameplay method, creation/revision reason, parent, semantic change record, and evidence/outcome summaries. Untested/unknown outcomes are explicit; explanations are model claims, not verified effects. The required live activity surface displays an actual version change, why it changed, its semantic changes, and the trial/measurement outcome or “not yet measured,” with inline expansion or links to the card and authorized source/events. At least one real authored improvement with linked gameplay-trial evidence is displayable. Authorized generated source may be displayed as escaped, non-executable text; viewing grants no execution, installation, activation, or additional data authority. Model-authored markup/scripts must not execute in the operator origin. A full library browser/editor or replay system is not required.
- [ ] **P22 — Two-provider task success.** The same declared bounded task achieves adapter-verified success under at least two strategic models from different providers, with unchanged GameHarness core and GameAdapter; only provider/model/configuration/credentials differ. Retain model/provider identities, conditions, actual attempts, failures and verifier evidence. This does not promise every provider or Ender Dragon completion with both models. P02 independently retains both auth categories; explicit compatible library imports are a separate P11 requirement.

## First reference integration: Minecraft

The implemented Minecraft adapter uses Java Edition 1.21.4, Survival, Normal difficulty, ordinary spawn/inventory and death rules, and no agent cheats or operator powers. Bounded native and actual-model episodes exercise these conditions; the complete-integration and full-game criteria below remain separate.

An actual Java 21 / Fabric 1.21.4 client owns filtered perception, smooth bounded aiming/held movement and legitimate interactions. It captures authentic frames after world/hand/HUD rendering and suppresses ordinary physical gameplay/menu callbacks and polling. A managed Fabric server requires session proof and rejects unrelated or same-name clients before they can displace the owned player. Control and binary video are separately authenticated; there is no automatic old-adapter fallback. Game access and server EULA consent remain operator responsibilities.

The implemented profile is `minecraft_assisted_rgb_360_r8_v1`: authorized structured state and one unsynchronized actor PNG, with camera-independent raycast sampling within eight blocks. Observation envelope 3 carries life, space and screen identity; the negotiated descriptor binds the effective profile configuration and capability schemas. Native semantic craft/equip operations use visible screens and one authoritative pointer. The broader profile target also includes assisted RGB/frustum and strict-visual conditions; those alternatives, audio and aligned capture are not delivered by this profile.

Prepared development or mechanical tasks may use explicitly declared initialization and independent feasibility checks. Keep privileged setup/scoring outside actor feedback and report the condition separately. Ordinary fresh-world efficacy and full-game completion retain ordinary terrain/inventory requirements; no prepared result is relabeled to satisfy them.

Hidden resources/structures, exact live concealed entity state, seeds, saves, evaluator state, raw native-client access and video backing data remain forbidden agent inputs. Last-seen memory receives no hidden live updates; real audio yields only coarse sound signals. Queries filter before counts/order/truncation/errors. Trusted raw client access grants no model/program/library world/chunk/entity shortcut.

Historical schema 2/preset `minecraft-observable-initial-r2` added session/life lineage; its original records retain that identity. Current eligible ItemEntity `item_name` exposes only represented registry identity, never exact dropped-stack count, NBT or custom hidden data. Motor profiles and route/target/free gaze remain bounded mechanical configuration, not hidden-world perception or authored tactics. `break_log` requires confirmed eligible removal; `collect_wood` separately requires receipted own-inventory gain, with the run baseline retained across death.

Low-level navigation may privately read bounded client-loaded collision/passability/headroom geometry around the avatar toward an already authorized known target/waypoint, including bounded local detours through cells not individually observed. It cannot expose that map, identify hidden materials/resources/entities, or use a global loaded-world planner to select an undiscovered cave, shortcut, corridor, or exploration route. Route discovery outside the local execution envelope needs authorized observation/replanning or neutral bounded failure. Local steering/path choice/timing may benefit from this declared geometry; this is a structured-information approximation, not human-identical perception or a zero-leakage claim. Apply the same permission in comparisons and prove the boundary through [operations fixtures](../operations-and-security.md#structured-observation-and-navigation), without an all-voxels-observed map requirement.

Paper Anti-Xray is optional defense in depth, never the sole filter; filtering must work when it is disabled. Record server flavor, exact game/server build, and effective per-world/dimension Anti-Xray configuration in evaluator-owned evidence, freezing them across matched runs. No Paper deployment or compatibility is established here; [upstream evidence](../upstream-reuse.md#structured-observation-and-navigation-evidence) records version-specific limitations.

Bounded capabilities include movement/look/input, interaction, digging, placing, crafting, and equipping with explicit choices. The model decides what to obtain, where to explore, and when to fight, retreat, or craft. There are no handwritten collect-wood, survive, explore, combat-strategy, or complete-game routines.

Reference-profile acceptance adds:

- [ ] **M01 — Complete Minecraft workflow.** The generic workflow and P01–P22 evidence are exercised with the targeted Normal Survival integration, including real first-person viewing, permitted mechanics, and meaningful progress in previously unseen worlds.
- [ ] **M02 — Full-game objective and honest status.** Support the first autonomous Ender Dragon defeat and ordinary return/exit transition from fresh ordinary spawn/inventory as a long-horizon objective. Preserve real full-game attempts, failures, interventions and independently verified progress/completion. A supplied arena, already-defeated world, smaller tool milestone or model completion claim cannot substitute. Until the actual completion chain is verified, the objective remains unachieved independently of workflow readiness.
- [ ] **M03 — Save and uncertain-effect recovery.** Prove the implemented Minecraft save/backup/reconnect behavior separately from agent summaries. Lost craft/place/consume results are not blindly retried. Restoring an older world snapshot explicitly branches or marks rollback and reconciles memory. This evidence establishes only the Minecraft adapter's documented capabilities.

## Selected implementation constraints

The backend uses Bun 1.3.14+, TypeScript and exact selected OMP packages. Electron owns a sandboxed TypeScript renderer built by Vite, the backend child lifecycle and readiness handshake. Authenticated HTTP JSON/SSE carry controls/events; `/v1/video` carries native binary frames separately. Renderer navigation, external links and IPC remain bounded; the desktop shell does not bypass session, Host/Origin or CSRF checks.

GameHarness must be language-agnostic at component boundaries. Performance-critical components may be implemented in native languages without modifying the agent runtime, skill format, or game adapter contracts. Runtime code is decomposed by lifecycle, scheduling/context, program execution, policies, providers/accounting, experience and evidence. TypeScript remains orchestration/providers/memory/evaluation; Java implements Fabric observation/motor/capture; skills remain JS. Rust needs a measured bottleneck, not speculative service extraction. Retain actual CPU/event-loop/observation/command/FPS/program-duration measurements.

The trusted backend owns SQLite records and immutable artifact references. Generated JavaScript runs in OS-isolated workers through brokered capabilities; ordinary `eval`, `vm`, or language workers alone do not establish a security boundary. The application binds loopback by default and authorizes control requests. Provider credentials, raw game/protocol state, environment files, and database access remain trusted.

These constraints preserve a game-neutral orchestration core while allowing the first integration's concrete bridge and renderer. Component ownership and supported extension interfaces belong in the [architecture](../architecture/overview.md) and [runtime contracts](../runtime-contracts.md); selected dependency evidence belongs in [upstream reuse](../upstream-reuse.md).
