# General-harness research scope

**LEGACY GENERAL-HARNESS RESEARCH.** These requirements describe the retained
experimental GameHarness system. They do not govern the ordinary
developer-written Java Survival player or prohibit its local strategy.
Ordinary play uses local execution with asynchronous configured-model advice.
Its current acceptance target is diamonds **and** Nether entry in one fresh
Normal Survival campaign. See [Survival evidence](../evidence/survival.md).

The research system asks a different question: can one strategic model observe,
author programs, act, inspect consequences and revise reusable procedures
through a game-neutral, isolated runtime? Minecraft is its first integration.
Other games require adapters and conformance evidence; a common interface does
not establish automatic support.

## Research authorship boundary

For this research condition, the principal model owns resource strategy,
destinations, procedural composition, reactive conditions and revision.
Infrastructure supplies connection lifecycle, permitted perception, bounded
mechanics, scheduling, isolation, providers, persistence, evidence and recovery.
A recipe helper executes a selected recipe; it does not recursively gather
prerequisites. Richer developer-authored players are explicit assistance or
comparator conditions. This distinction must not be misapplied to ordinary
Survival, where developer-written strategy is the requested primary system.

Public game documentation, recipes, pretrained knowledge and brokered retrieval
are permitted. Explanations use source/events, not hidden chain of thought.
Information permission is independent of whether observations arrive as images
or structured data. Unknown state stays unknown.

## Workflow and release boundaries

An operator on the supported Linux host prepares lawful game access, connects
an entitled provider, selects an adapter/task/profile and immutable experience
snapshot, starts through host preflight, watches actual play, controls execution
and inspects retained outcomes. Configuration is not verified connectivity.
Warm selections use normal compatibility/freshness gates, not mandatory
regeneration. Start, pause, resume and stop reflect acknowledged runtime state.

Ordinary death changes life inside the same session/run. Old-life work is
fenced; authentic death video remains available; only explicit model-selected
vanilla respawn starts a new life. Saved-dead startup never auto-respawns.
Pause, Stop run and goal closure retain a healthy session after actual drain;
world stop/replacement and application close own process teardown.

Report workflow readiness, useful continuity, adapter support and verified task
outcome separately. An unfinished objective does not erase working mechanisms;
working mechanisms do not establish objective completion.

Required research work includes one complete integration, two auth categories,
two-provider bounded-task success, evidence-qualified experience, registered
comparisons and progressive reliability. Jev is optional for ordinary code-only
execution. Finer ablations, replay/export UI, full library editors, extra
dashboards and midrun model switching are optional.

Multiple players, hosted multiuser service, arbitrary platform compatibility,
reinforcement learning, fine-tuning, human strategy trials, speedrunning records
and scientific novelty are not initial requirements. A second adapter is not
required. Component boundaries stay language-agnostic: TypeScript orchestrates,
Java handles native Minecraft, generated programs use JS. Native extraction
needs measured CPU, event-loop, observation, command, FPS or execution evidence.
An ordinary language VM is not an isolation boundary.
